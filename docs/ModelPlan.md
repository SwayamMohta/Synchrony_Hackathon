# Model Plan — How the Underwriting Engine Decides

Plain-English explanation of how a credit application becomes a decision. No jargon (and where a technical word is unavoidable, it's explained).

---

## In one sentence

An analyst (or a pre-filled demo scenario) enters a person's financial details; the system builds a credit-risk score from those details, checks a few fraud and policy rules, and returns APPROVE / REFER / DECLINE — each with a plain-English reason.

---

## 1. What gets entered (all explicit and controllable)

Nothing about a person's finances is invented or generated behind the scenes. Everything the model sees is either **entered on the form** or **computed by the system** from those entries.

> ⚠️ All credit and bank details below are **demo/simulated input** — clearly labelled as such in the UI. They are NOT verified bureau data.

### A. Identity
- **Applicant ID** — identifies the application and links it to fraud-history/audit records. It does **not** generate any financial profile.

### B. Credit history (bureau-style — demo/simulated)
| Field | Meaning |
|---|---|
| Credit utilization | How much of their available credit they are using (e.g. 30%) |
| Open credit lines/loans | Number of active credit cards and loans |
| 30–59 day late payments | Count of payments 30–59 days late |
| 60–89 day late payments | Count of payments 60–89 days late |
| 90+ day late payments | Count of payments 90+ days late |
| Real-estate loans | Number of mortgages/property loans |
| Monthly debt payments | Their monthly debt payments (used for the debt ratio) |

### C. Bank account (cash-flow — demo/simulated)
| Field | Meaning |
|---|---|
| Average monthly income | Money coming in each month |
| Average monthly expenses | Money going out each month |
| Overdraft count (90 days) | How many times they overdrew recently |

### D. About the person
| Field | Meaning |
|---|---|
| Age | Their age |
| Dependents | Number of people they support |
| Annual income | Yearly income (we convert to monthly) |

### E. The loan request
| Field | Meaning |
|---|---|
| Requested loan amount | How much they want to borrow |

### F. Fraud signals (system-observed, not entered)
These are **generated by the system** from application history — the applicant does not type them:
- Applications per device in the last 24h
- Applications per IP address in the last 24h
- Device/identity consistency (does one person keep using different devices?)

---

## 2. What the system calculates (derived, not entered)

The user does not enter these — the system computes them:

| Derived value | Formula | Used for |
|---|---|---|
| Monthly income | annual income ÷ 12 | credit model |
| **Expense-to-income ratio** (cash-flow) | monthly expenses ÷ monthly income | policy rule (the 65% cap) |
| **Debt ratio** (bureau/GMSC) | (monthly debt payments + alimony + living costs) ÷ monthly gross income | credit model |
| **Affordability** | requested amount ÷ monthly income | refer trigger (policy) |

> These two ratios are **deliberately kept separate and clearly named** — "expense-to-income ratio" (bank spending) is NOT the same as "debt ratio" (bureau debt obligations). They appear with different names in both the code and the UI.
>
> For the debt ratio, "alimony" is not collected (treated as 0) and "living costs" maps to the entered *average monthly expenses*; "monthly gross income" is *annual income ÷ 12* — matching the GMSC Data Dictionary ("Monthly debt payments, alimony, living costs divided by monthly gross income").

---

## 3. The credit-risk model

We feed **10 numbers** (the exact same 10 columns used to train the model) into a machine-learning model.

| # | Feature (exact training name) | Where it comes from |
|---|---|---|
| 1 | RevolvingUtilizationOfUnsecuredLines | Credit utilization (entered) |
| 2 | age | Age (entered) |
| 3 | NumberOfTime30-59DaysPastDueNotWorse | 30–59 day lates (entered) |
| 4 | DebtRatio | (monthly debt payments + alimony + living costs) ÷ monthly gross income (derived) |
| 5 | MonthlyIncome | annual income ÷ 12 (derived) |
| 6 | NumberOfOpenCreditLinesAndLoans | Open credit lines/loans (entered) |
| 7 | NumberOfTimes90DaysLate | 90+ day lates (entered) |
| 8 | NumberRealEstateLoansOrLines | Real-estate loans (entered) |
| 9 | NumberOfTime60-89DaysPastDueNotWorse | 60–89 day lates (entered) |
| 10 | NumberOfDependents | Dependents (entered) |

- The model is **XGBoost**, trained on **150,000 real past borrowers** (the public "Give Me Some Credit" dataset).
- **Training and inference use the exact same feature names, order, meaning, and units** — so what the model learned applies correctly.
- Cash-flow and fraud data are **never** forced into the training data (they don't exist there).

**Output:** a **predicted credit-risk score** from 0 to 1 (higher = riskier).

> ⚠️ We call it a *"predicted credit-risk score"*, not an exact probability of default. We have not calibrated the model to real-world default rates, so we do **not** claim "there is exactly an X% chance of default."

---

## 4. The fraud check (rule-based — actually works in the demo)

Simple "if this, then that" rules over the fraud signals:

| Signal | Rule |
|---|---|
| ≥ 5 applications from same IP in 24h | add 0.5 |
| ≥ 4 applications from same device in 24h | add 0.3 |
| identity keeps switching devices | add 0.4 |

The score is capped at 1.0. Higher = more suspicious. It is a **rule-based fraud risk score** (deterministic "if this, then that" rules), **not a calibrated probability**.

How this is demonstrated without random data:
- The system keeps a **small application history** (keyed by device/IP).
- The **"Suspicious" demo scenario** uses a device/IP that already has many recent applications in that history → high velocity → high fraud score.
- The normal scenarios use fresh device/IP → low fraud score.

So the demo can show **normal → low fraud** and **suspicious → high fraud**, deterministically. (A trained ML fraud model is optional and not required.)

---

## 5. The policy engine (hard rules the model cannot override)

These are fixed guardrails. Even a perfect credit score cannot override them.

### Hard rules → automatic DECLINE

| Rule | Fails if |
|---|---|
| Minimum age | under 18 |
| Expense-to-income ratio | spending more than 65% of income |
| Severe delinquency | 4 or more payments 90+ days late |

> Application velocity (many applications from one device/IP) is handled by the **fraud check** (section 4) → REFER, not as a hard decline here.

### Refer triggers → human review (not an automatic decline)

| Trigger | When |
|---|---|
| Affordability | requested amount is large relative to monthly income (prototype: more than 6× monthly income) |
| Fraud | rule-based fraud risk score > 0.70 |
| Uncertainty | credit-risk score between 0.35 and 0.60 |

> ⚠️ **These thresholds are prototype/demo values**, not statistically optimised or production-approved. They are chosen to demonstrate the mechanics, and should be treated as such.

---

## 6. The final decision

In strict order:

1. Broke any hard rule? → **DECLINE**
2. Rule-based fraud risk score > 0.70? → **REFER**
3. Requesting a large amount relative to monthly income (affordability)? → **REFER**
4. Credit-risk score ≥ 0.60? → **DECLINE**
5. Credit-risk score ≥ 0.35? → **REFER** (uncertain)
6. Otherwise → **APPROVE**

> ⚠️ The credit thresholds (0.35 / 0.60), fraud threshold (0.70), and affordability threshold (6× monthly income) are **prototype values for the demo**, not production policy.

---

## 7. The explanation — two separate things

We keep these clearly distinct:

1. **SHAP** — explains *what influenced the machine model's risk prediction* (e.g. "high credit utilisation pushed the score up").
2. **Policy / fraud reason codes** — explain *why the final decision* was APPROVE / REFER / DECLINE (e.g. "Debt-to-income ratio exceeds limit").

They are shown separately in the UI. **SHAP is NOT used to explain a policy-rule decline** — if the model predicted low risk but a hard rule declined the applicant, the reason shown is the policy rule, not SHAP.

---

## 8. Audit trail (reproducible)

Every decision is saved with everything needed to reproduce it:

- the full input snapshot (the final feature vector + the raw entered inputs)
- decision
- credit-risk score
- fraud score (rule-based fraud risk score)
- reason codes (policy + fraud)
- model version
- policy version
- feature-schema version
- timestamp and request ID

We only claim **replayability when all these inputs are stored** — which they are, so a decision can be reconstructed exactly.

---

## 9. Demo scenarios (pre-filled, editable)

The form provides three one-click pre-filled scenarios (the evaluator can see and edit every field before submitting):

1. **Low-risk thin-file applicant** — little credit history, but responsible finances → expected APPROVE.
2. **High-debt applicant** — expense-to-income ratio clearly above the 65% cap (84%) → expected DECLINE (policy).
3. **Suspicious/fraudulent applicant** — high device/IP velocity → expected REFER/DECLINE (fraud).

## 10. What we use (in plain terms)

| Tool | What it does |
|---|---|
| Python + FastAPI | Backend server (receives the application, runs the checks) |
| XGBoost | Credit-risk model (trained on 150k real borrowers) |
| Logistic Regression | Simpler baseline model, kept only for comparison |
| SHAP | Explains the model's risk prediction |
| React + Vite + Recharts | Web page (form + result + chart) |
| PostgreSQL + pgvector | Database for audit records (and later, policy search) |
| Rule-based fraud | Simple "if this then that" fraud checks (no ML needed) |
| Dataset | "Give Me Some Credit" (public, 150k real borrowers) |

---

## 11. End-to-end flow

1. Analyst picks a demo scenario (or enters values) → all inputs visible and editable.
2. System computes derived values (monthly income, expense-to-income ratio, debt ratio, affordability).
3. System computes fraud signals from application history (device/IP velocity).
4. System builds the 10 features (same names/order/units as training).
5. **XGBoost** produces a predicted credit-risk score.
6. **Fraud rules** produce a rule-based fraud risk score.
7. **Policy engine** checks the hard rules (age, expense ratio, delinquency, affordability, velocity).
8. **Decision function** combines them → APPROVE / REFER / DECLINE.
9. **SHAP** explains the model's risk; **reason codes** explain the decision (shown separately).
10. Everything (inputs, feature vector, scores, reasons, versions) is written to the **audit log**.

---

## 12. Scope (kept realistic)

Core: real GMSC dataset · XGBoost + logistic regression · controlled inputs · deterministic fraud signals · deterministic policy engine · APPROVE/REFER/DECLINE · SHAP + reason codes · audit trail · React + FastAPI + PostgreSQL · minimal RAG (local embeddings + pgvector + OpenAI).

Optional / only-if-time: LangGraph/agents, Plaid, complex fraud ML, cloud deployment, extensive MLOps, advanced monitoring.
